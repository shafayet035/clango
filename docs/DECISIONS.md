# Clango — Decision Log

Short ADR-style entries for every non-obvious design choice. Append new entries; never rewrite
history — supersede with a new entry and mark the old one `Superseded by D-0xx`.

Format: **Status · Date · Context · Decision · Consequences.**

Source spec: [`docs/SPEC.md`](./SPEC.md). Platform facts were verified against the Cloudflare docs
on 2026-09-22; re-verify per milestone and add an entry when the docs disagree with the spec.

---

## D-001 — Framework name: Clango

- **Status:** Accepted · 2026-09-22
- **Context:** The spec's working name was "Cirrus". The project directory is `clango`.
- **Decision:** Name the framework **Clango**. Packages are `@clango/*`, config is
  `clango.config.ts`, the CLI binary is `clango`, framework tables are `clango_*`.
- **Consequences:** All v1 references to Cirrus in `docs/SPEC.md` were renamed. The name is
  provisional until first publish; a rename later is mechanical but touches package names and the
  CLI.

## D-002 — Primary keys: ULID strings

- **Status:** Accepted · 2026-09-22
- **Context:** Django defaults to integer autoincrement. ULIDs are sortable, opaque, and
  client-generatable; integer keys are smaller and reveal count.
- **Decision:** Every model gets a 26-character ULID string `id` generated by the framework.
- **Consequences:** IDs are sortable by creation time without a separate column. TEXT primary keys
  cost more index space than integers and SQLite has no clustered index on them — acceptable at
  D1's 10 GB scale, but bulk-insert benchmarks in M1 should confirm. Export/import must preserve
  IDs.

## D-003 — Auth library: Better Auth as the reference adapter

- **Status:** Accepted · 2026-09-22
- **Context:** Identity must be delegated behind an `AuthAdapter`; candidates were Better Auth,
  Clerk, and Auth.js.
- **Decision:** Ship **Better Auth** as the reference adapter (`packages/auth-better-auth`).
  Authorization (permissions, groups, `isStaff`/`isSuperuser`) stays in Clango-owned D1 tables.
- **Consequences:** Better Auth runs in the same Worker as the app, so "external" means
  library-owned, not out-of-process. Session lookup is a hot path — enable Better Auth's cookie
  cache. Swapping providers later only requires a new adapter, because no authorization data lives
  in the auth library's schema.

## D-004 — Admin UI: minimal custom components

- **Status:** Accepted · 2026-09-22
- **Context:** The admin SPA must be generic and shipped as static assets. A component library
  (e.g. shadcn/ui) would speed up polish but adds dependency weight and upgrade churn.
- **Decision:** Build the generic views with **minimal custom components**. No runtime component
  library dependency in v1. Custom widgets can be registered as React components in M7.
- **Consequences:** More UI code to write for M3, but full control over bundle size and no
  third-party upgrade treadmill. Revisit if M3 velocity suffers.

## D-005 — Multi-tenancy deferred to M6

- **Status:** Accepted · 2026-09-22
- **Context:** Database-per-tenant is central to the scaling story but not needed for the M1–M3
  vertical slice.
- **Decision:** Multi-tenancy ships in **M6**, gated on the tenant-resolution spike (D-012).
- **Consequences:** The `DatabaseRouter` interface must exist from M1 so tenant routing can be added
  without reshaping the ORM. No tenant-aware code before M6.

## D-006 — `decimal` stored as integer minor units

- **Status:** Accepted · 2026-09-22
- **Context:** v1 mapped `decimal` to `INTEGER / TEXT`. SQLite gives TEXT columns lexicographic
  ordering, so decimals stored as TEXT break range filters and sorts. REAL is lossy for money.
- **Decision:** `fields.decimal({ scale })` stores **integer minor units** (e.g. `scale: 2` → cents)
  in an INTEGER column. The ORM converts on read and write.
- **Consequences:** Exact arithmetic and correct ordering. Values are bounded by SQLite's 64-bit
  integer range — document a maximum. Aggregations must be done in minor units and converted at the
  edge.

## D-007 — Table rebuilds use `defer_foreign_keys`, not `foreign_keys=OFF`

- **Status:** Accepted, **partly superseded by D-022 and D-023** · 2026-09-22
- **Context:** SQLite cannot alter/drop most columns in place, so migrations rebuild tables. v1
  specified doing this inside `PRAGMA foreign_keys=OFF`. Cloudflare's D1 docs state that PRAGMA
  statements **only apply to the current transaction**, and migration files are applied
  statement-by-statement — so a leading `foreign_keys=off` does not govern the following DDL. The
  docs explicitly recommend `PRAGMA defer_foreign_keys = on` for migrations.
- **Decision:** The migration emitter wraps each rebuild in an explicit `BEGIN; … COMMIT;`, sets
  `PRAGMA defer_foreign_keys = on` inside that transaction ahead of the DDL, and never relies on
  `foreign_keys=off` semantics.
- **Consequences:** Rebuilds are atomic and FK-safe. **`ON DELETE CASCADE` still fires under
  deferral**, so row-copy order must not trigger cascades. M1 must test a rebuild with a child FK
  row and assert that violating rows fail at `COMMIT`. Don't assume migration files are applied
  atomically on their own — the explicit transaction is required.

## D-008 — Search uses FTS5 `MATCH`; `LIKE` is restricted

- **Status:** Accepted · 2026-09-22
- **Context:** D1 caps `LIKE`/`GLOB` patterns at **50 bytes**. Admin `searchFields` and free-text
  filters implemented with `LIKE '%term%'` would fail as soon as a user typed ~50 characters.
- **Decision:** All user-supplied search goes through FTS5 `MATCH` (fields declared
  `searchable: true`). `LIKE` is reserved for short, server-controlled values (slug lookups, known
  prefixes).
- **Consequences:** Admin search requires the FTS5 virtual table and sync triggers to exist. Trigger
  creation inside `wrangler d1 migrations apply` is a known risk (see D-016) and needs a dedicated
  test.

## D-009 — Bounded admin counts

- **Status:** Accepted · 2026-09-22
- **Context:** D1 bills rows read, and a bare `COUNT(*)` scans the whole table. The spec wants exact
  counts up to 10,000 and "10,000+" beyond.
- **Decision:** Counts are computed as `SELECT COUNT(*) FROM (SELECT 1 FROM t WHERE … LIMIT 10001)`
  (or by fetching `limit + 1` rows). A bare `COUNT(*)` is never issued.
- **Consequences:** Cost per list view is bounded regardless of table size. Counts above 10,000 are
  approximate ("10,000+"), which the UI must make clear.

## D-010 — R2 presigning via `aws4fetch` and a dedicated S3 API token

- **Status:** Accepted · 2026-09-22
- **Context:** The R2 binding cannot sign URLs. Presigned URLs require AWS Signature v4 and an R2
  S3 API token (access key + secret) plus the account ID. The Cloudflare docs recommend `aws4fetch`
  for Workers (fetch + SubtleCrypto).
- **Decision:** Presigned uploads/downloads are signed in the Worker with **`aws4fetch`** using
  dedicated R2 S3 credentials stored as Worker secrets. Uploads use `PUT`; expiry defaults to ≤15
  minutes; the bucket gets a CORS policy for the admin origin.
- **Consequences:** Only `GET`/`HEAD`/`PUT`/`DELETE` are available — **no POST multipart form
  uploads**. Presigned URLs **cannot be revoked** before expiry, so TTLs stay short and the key is
  untrusted until the record is saved. Orphaned uploads (URL issued, record never saved) are swept
  by a scheduled task after 24 h.

## D-011 — Bulk queue payloads are query descriptors, not id lists

- **Status:** Accepted · 2026-09-22
- **Context:** Queues cap messages at 128 KB, and an uncaught error retries the entire batch. A
  "publish everything matching this filter" action can match far more rows than fit in one message.
- **Decision:** Bulk admin actions enqueue a **query descriptor** (model, filters, cursor) rather
  than a list of IDs. The consumer pages through the filter and processes in bounded chunks. Every
  message is handled in its own `try/catch` with explicit `ack()`/`retry()`.
- **Consequences:** Actions remain idempotent and resumable, and message size is independent of the
  result-set size. The consumer must re-run the filter, so semantics are "matching at consumption
  time" — acceptable for admin bulk actions, and worth documenting.

## D-012 — Tenant resolution requires an M6 spike (binding limit)

- **Status:** Accepted · 2026-09-22
- **Context:** v1 sketched a tenant resolver returning a D1 database ID used by the ORM. Workers
  bindings are **static**, and a single Worker script can bind roughly **5,000** D1 databases
  (account cap 50,000). There is no runtime "use this database ID as a binding" mechanism.
- **Decision:** Defer the mechanism to an **M6 spike** that compares three options: (1) D1 HTTP API
  with an API token, (2) Workers for Platforms / dispatch namespaces, (3) a bounded binding pool
  with tenant sharding. Record the chosen mechanism here before building `migrate --all-tenants`.
- **Consequences:** No tenant-routing code before the spike. The `DatabaseRouter` interface (D-013)
  must be able to express "resolve a connection at request time" so the chosen mechanism can slot
  in. `migrate --all-tenants` needs its own Cloudflare API rate-limit/backoff strategy.

## D-013 — D1 driver behind an interface from day one

- **Status:** Accepted · 2026-09-22
- **Context:** Projects may outgrow a single D1 database or need Postgres features. Rewriting model
  definitions later would be prohibitively expensive.
- **Decision:** Keep the ORM layer behind a driver interface. Only the D1 driver ships in v1, but
  the interface exists from M1.
- **Consequences:** Slightly more indirection in the ORM. **Hyperdrive is a connection pooler for
  external Postgres/MySQL, not a database provider** — the escape hatch still requires the project
  to bring a Postgres. Docs must not imply otherwise.

## D-014 — D1 Sessions API per request

- **Status:** Accepted · 2026-09-22
- **Context:** Read replication lowers read latency and scales read throughput, but replica lag
  creates consistency hazards for read-after-write.
- **Decision:** Open a D1 session per request (`env.DB.withSession()`) and close it in a `finally`.
  Reads go through the session so users read their own writes; writes are transparently forwarded to
  the primary.
- **Consequences:** `withSession()` is safe even on databases without read replication enabled, so
  the code path ships before the feature is switched on per database. Long-running backfills use a
  session timeout up to 15 minutes instead of unbounded statements.

## D-015 — Admin log written in the same batch as the mutation

- **Status:** Accepted · 2026-09-22
- **Context:** Every admin write is recorded in `clango_admin_log`. On a single-threaded D1
  database, a second write per mutation doubles write pressure and can leave the log out of sync if
  it fails.
- **Decision:** Write the log entry in the **same `db.batch()`** as the mutation. Keep the diff
  payload small and make log retention configurable.
- **Consequences:** Log and mutation are atomic. The diff must be size-bounded (2 MB row cap) —
  truncate large text/JSON values with an explicit marker.

## D-016 — Verify trigger creation inside `wrangler d1 migrations apply`

- **Status:** Proposed · 2026-09-22
- **Context:** FTS5 sync requires `CREATE TRIGGER`. There are community reports of trigger creation
  failing when run through `wrangler d1 migrations apply`, while the SQL itself is valid in D1.
- **Decision (proposed):** Add a dedicated M1 test that applies an FTS5 virtual table plus its sync
  triggers via the migrations command. If it fails, apply trigger creation from the `clango migrate`
  command via `d1 execute` as a follow-up statement, and record the workaround here.
- **Consequences:** Search correctness depends on this passing. Do not ship M2 search before this is
  resolved.

## D-017 — `defineModel` uses two-pass inference with phantom-typed references

- **Status:** Accepted · 2026-09-22
- **Context:** `defineModel` must infer row/insert/update types from field definitions and support
  circular relations (`Post → Author`, `Author → Post`). Naive generic inference produces slow
  editors and unreadable errors.
- **Decision:** Capture fields `as const`, derive row/insert/update types with mapped types, and
  make `foreignKey`/`manyToMany` take a lazy `() => Model` that returns a `ModelRef<T>` carrying
  only a **phantom type** (never a runtime value). The runtime graph stays acyclic.
- **Consequences:** Types resolve without circularity. `tsc --extendedDiagnostics` on
  `examples/blog` is recorded in M1 and treated as an acceptance criterion, not a nice-to-have.

## D-018 — Static asset routing config for the admin SPA

- **Status:** Accepted · 2026-09-22
- **Context:** With `not_found_handling: "single-page-application"`, every non-asset path returns
  `index.html` — including unknown `/api/*` requests, which must return JSON 404s.
- **Decision:** Configure `run_worker_first` with explicit positive paths and a negative pattern for
  the SPA's own assets:

  ```jsonc
  "assets": {
    "directory": "./packages/admin-ui/dist",
    "binding": "ASSETS",
    "not_found_handling": "single-page-application",
    "run_worker_first": ["/api/*", "/admin/api/*", "/files/*", "!/admin/assets/*"]
  }
  ```

- **Consequences:** Unknown API paths 404 as JSON; SPA deep links (`/admin/posts/123`) serve the
  shell. Both behaviours are covered by routing tests in M3.

## D-019 — Vitest integration uses `@cloudflare/vitest-plugin`

- **Status:** Accepted · 2026-09-22
- **Context:** The spec named `@cloudflare/vitest-pool-workers`. The Cloudflare docs (last updated
  2026-08-20) now document `@cloudflare/vitest-plugin` and its `cloudflareTest()` Vite plugin;
  `@cloudflare/vitest-pool-workers` remains published as the legacy package. The docs also deprecate
  `SELF` and `env` from `cloudflare:test` in favour of `env` and `exports.default.fetch()` from
  `cloudflare:workers`.
- **Decision:** Use `@cloudflare/vitest-plugin` (v1.x, requires Vitest 4). Configure it as a Vite
  plugin:

  ```ts
  // vitest.config.ts
  import { cloudflareTest } from "@cloudflare/vitest-plugin";
  import { defineConfig } from "vitest/config";

  export default defineConfig({
    plugins: [cloudflareTest({ wrangler: { configPath: "./wrangler.jsonc" } })],
  });
  ```

  Tests import `{ env, exports }` from `cloudflare:workers`. D1 migrations in tests use
  `readD1Migrations()` + `applyD1Migrations()` from the same package (wired up in M1).

- **Consequences:** Vitest is pinned to `^4.1.0` (the plugin's peer range). `readD1Migrations` is
  exported from the package root, not `@cloudflare/vitest-plugin/config` as the docs currently
  suggest — verify on upgrade. `docs/SPEC.md` was updated to match.

## D-020 — Source-first package exports (no build step yet)

- **Status:** Accepted · 2026-09-22
- **Context:** M0 needs a working workspace, not publishable artifacts. Adding a bundler/`tsc`
  build per package now would slow the loop and add config surface for no benefit.
- **Decision:** Packages export TypeScript source directly (`"exports": { ".": "./src/index.ts" }`).
  Wrangler (esbuild) and Vitest transform workspace dependencies from source. `wrangler types`
  generates `worker-configuration.d.ts`, which is committed.
- **Consequences:** No `dist/` and no publish step until the first release milestone. Before
  publishing, add per-package builds and point `exports` at compiled output; CI bundle-size tracking
  (spec: "Bundle size") also lands then. Consumers outside the monorepo cannot install these
  packages yet.

## D-021 — TypeScript pinned to 5.x

- **Status:** Accepted · 2026-09-22
- **Context:** `pnpm add typescript` resolves to TypeScript 7.x, but `typescript-eslint` 8.x declares
  a peer range of `>=4.8.4 <6.1.0`, so linting breaks on TS 7. TypeScript 7 is the native compiler
  and ecosystem support is still landing.
- **Decision:** Pin TypeScript to the latest 5.x (`^5.9.3`). Revisit when typescript-eslint supports
  TypeScript 7 and Cloudflare tooling declares compatibility.
- **Consequences:** The repo stays on a supported, well-tested toolchain. Watch for the TS 7 upgrade
  and treat it as a deliberate, tested change rather than a floating dependency bump.

## D-022 — Migrations never open their own transaction

- **Status:** Accepted · 2026-09-22 · refines D-007
- **Context:** D-007 told the emitter to wrap each rebuild in an explicit `BEGIN; … COMMIT;`. M1
  verified that D1 already runs a migration inside a single transaction: `applyD1Migrations` sends
  every statement of a file plus the ledger insert through one `db.batch()`, and
  `wrangler d1 migrations apply` applies the file atomically. Emitting `BEGIN` therefore fails with
  "cannot start a transaction within a transaction", which the D1 docs also warn about.
- **Decision:** The emitter never emits transaction control. It emits `PRAGMA defer_foreign_keys =
on` once at the top of any migration that rebuilds or drops a table, and relies on D1's own
  transaction for atomicity.
- **Consequences:** Foreign-key enforcement is deferred to the end of the migration, so a rebuild
  can drop and recreate a table without tripping constraints. The pragma's transaction scope is
  exactly the migration, which is what makes this work. Verified end to end through both
  `db.batch()` and `wrangler d1 migrations apply --local` (15 statements, including triggers).

## D-023 — Cascade-safe table rebuilds by backing up child rows

- **Status:** Accepted · 2026-09-22 · supersedes the rebuild advice in D-007
- **Context:** Rebuilding a table that children reference with `ON DELETE CASCADE` **destroyed those
  children**. SQLite's `DROP TABLE` performs an implicit `DELETE` while foreign keys are enabled,
  and that fires cascade actions — so `DROP TABLE blog_author` deleted every `blog_post` row before
  the rename restored the table. Deferring foreign keys does _not_ defer cascades. This was found by
  the M1 integration test, not by inspection.
- **Decision:** Before any rebuild, `planMigration` computes the transitive closure of tables that
  reference a rebuilt table with `ON DELETE CASCADE` or `ON DELETE SET NULL`, copies each to a
  `<table>__clango_bak` table, and restores them after all rebuilds. `ON DELETE RESTRICT` cannot be
  deferred by SQLite and blocks a rebuild outright, so the planner rejects it with an explanatory
  error. A migration that rebuilds both a parent and its cascade dependents is also rejected, with
  advice to split it, rather than risking silent data loss.
- **Consequences:** Parent rebuilds preserve child rows and `PRAGMA foreign_key_check` is clean
  afterwards. Migrations carry extra backup/restore statements, which is cheap next to data loss.
  Tests in `packages/migrate/test/d1.test.ts` assert child rows survive and cascades still fire.

## D-024 — `PRAGMA legacy_alter_table` is not usable on D1

- **Status:** Accepted · 2026-09-22
- **Context:** The obvious fix for D-023 is to rename the table out of the way with
  `legacy_alter_table = on` so child `REFERENCES` clauses are not rewritten and no cascade fires.
  M1 tested this: D1 accepted the pragma but `ALTER TABLE ... RENAME` still rewrote the child's
  foreign key to the archived name, leaving it pointing at a dropped table.
- **Decision:** Do not rely on `legacy_alter_table`. Cascade safety is handled by D-023 instead.
- **Consequences:** One fewer D1 pragma in the emitted SQL. Recorded so the approach is not
  re-attempted; if Cloudflare fixes the pragma, D-023's backup/restore can be revisited.

## D-025 — The Drizzle schema is built at runtime and carries no foreign keys

- **Status:** Accepted · 2026-09-22
- **Context:** Option (a) versus (b) for producing the Drizzle schema: build `sqliteTable()` from the
  registry at import time, or generate a `schema.ts` file. A generated file is a second source of
  truth that can drift, and the registry already carries everything needed. Foreign keys were
  considered for the runtime schema but need the target table object, which reintroduces circular
  initialisation for mutually-referencing models.
- **Decision:** `buildTable(model)` constructs the Drizzle table from the field definitions at
  runtime. Foreign-key metadata is omitted — SQLite enforces the constraints through the DDL the
  migration engine emits, and Drizzle does not need them for query building.
- **Consequences:** No generated schema file and no drift; `schemaFor(config)` is the single entry
  point. The trade-off is weaker static Drizzle types (columns are reached through `SQLiteTable`),
  which the typed query layer in M2 will address. An integration test in `packages/orm` round-trips
  `Date`, `boolean`, `json` and `decimal` values through Drizzle against the migrated schema, and
  asserts the foreign key declared by the migration rejects orphan rows.

## D-026 — `@clango/cli` is bundled with esbuild

- **Status:** Accepted · 2026-09-22 · refines D-020
- **Context:** D-020 chose source-first exports with no build step, which works for runtime packages
  because wrangler and Vitest transform them. The CLI cannot: Node refuses to type-strip files
  resolved through `node_modules`, and the project config is a `.ts` file that must be loaded at
  runtime.
- **Decision:** `@clango/cli` bundles `src/cli.ts` to `dist/cli.js` with esbuild (Node platform, ESM,
  `esbuild` marked external because it ships CommonJS with dynamic requires). A `prepare` script
  builds it on install, and `bin.clango` points at the bundle. The project config is bundled the same
  way into `node_modules/.clango/config.mjs`, so bare imports in the config resolve against the
  project.
- **Consequences:** The CLI needs a build step; every other package stays source-first. Node-only
  logic is confined to `packages/cli`, and the pure modules (argument parsing, slugging) are still
  tested in the Workers pool by importing them directly rather than through the package barrel —
  importing the barrel would drag `esbuild` into the test bundle.

## D-027 — Migrations live in `migrations/<database>/`

- **Status:** Accepted · 2026-09-22
- **Context:** A project can route models to several D1 databases (D-012), each with its own ledger.
  `wrangler d1 migrations apply` reads the directory from the binding's `migrations_dir` and has no
  `--migrations-dir` flag, so the layout has to be predictable and declared in `wrangler.jsonc`.
- **Decision:** `clango makemigrations` writes `<migrations-dir>/<database>/NNNN_name.sql` plus a
  committed `_snapshot.json` in the same directory. The D1 binding declares
  `migrations_dir: "migrations/<database>"`. `clango migrate` delegates to wrangler per database.
- **Consequences:** One directory per database, no ambiguity, and wrangler's ledger (`d1_migrations`)
  is authoritative. `--migrations-dir` exists for makemigrations only; changing it means updating
  `wrangler.jsonc` too, and the failure message says so.

## D-028 — `cloudflareTest` async configuration must return the wrangler options

- **Status:** Accepted · 2026-09-22 · refines D-019
- **Context:** To read D1 migrations from disk, the blog example passes an async function to
  `cloudflareTest()`. Returning only `{ miniflare: { bindings: … } }` silently **dropped the
  wrangler-derived bindings**, so `env.DB_MAIN` was `undefined` and tests failed with a confusing
  "parameter 1 is not of type D1Database". The async form replaces the options rather than merging
  with a separate `wrangler` key.
- **Decision:** When using the async form of `cloudflareTest`, always return the `wrangler` options
  alongside `miniflare`. Additionally, apply migrations inside a `beforeAll` in the test file rather
  than a Vitest `setupFiles` entry, because setup files run in the pool's runner context where the
  app's bindings are not visible.
- **Consequences:** Both gotchas are documented in `CLAUDE.md`. They cost real debugging time in M1.

## D-029 — REST exposure is opt-in per model and per operation

- **Status:** Accepted · 2026-09-22
- **Context:** A model definition is the single source of truth, so it is the natural place to say
  whether the model is reachable over HTTP. Mounting every model by default would make every table
  public the moment it is defined.
- **Decision:** Nothing is exposed unless a model declares `api: { enabled: true }`. Within an
  exposed model, `ops` selects a subset of `list`, `retrieve`, `create`, `update`, `delete`;
  omitting `ops` enables all five. A disabled operation is simply **not mounted**, so it returns
  `404` rather than `403`.
- **Consequences:** Leaking a model requires an explicit opt-in, and read-only models are expressed
  by omission (`ops: ["list", "retrieve"]`, as the blog does for `Tag`). The trade-off is that a
  client cannot discover "this exists but you may not do that"; that distinction belongs to M4's
  permission layer, which will return `403` for authenticated-but-unauthorised requests.

## D-030 — Keyset pagination cursors are null-safe and direction-aware

- **Status:** Accepted · 2026-09-22
- **Context:** The spec requires cursor pagination everywhere and no large `OFFSET`. Keyset
  pagination has two sharp edges on SQLite: `NULL` sorts first for `ASC` and last for `DESC`, so a
  naive `column < ?` comparison silently drops or repeats rows for nullable sort keys (the blog's
  default ordering is `-publishedAt`, which is nullable), and models mix directions once `id` is
  appended as a tie breaker.
- **Decision:** A cursor is base64url-encoded JSON carrying the **ordering signature** and the sort
  values of the last row. `planMigration`-style keyset predicates are built as an `OR` chain of
  `(prefix IS cursor) AND (key after cursor)`, with the ascending branch also matching
  `cursor IS NULL AND key IS NOT NULL` and the descending branch matching
  `cursor IS NOT NULL AND key IS NULL`. The ordering signature is compared on the way in, so
  changing `order` between pages is a `400` rather than a silently wrong page. Values are converted
  to their driver representation (epoch milliseconds, `0`/`1`) because raw `sql` fragments bypass
  Drizzle's column mapping — passing a `Date` straight to D1 fails with `D1_TYPE_ERROR`.
- **Consequences:** Pages are stable across nullable and mixed-direction orderings; a pagination
  walk in `packages/api/test/api.test.ts` asserts every row is seen exactly once. The cost is a more
  verbose predicate and a cursor that is not human-readable.

## D-031 — List counts are capped, never unbounded

- **Status:** Accepted · 2026-09-22 · implements D-009
- **Context:** D-009 requires bounded counts; D1 bills rows read, so a bare `COUNT(*)` on a large
  table is both slow and expensive.
- **Decision:** The list query runs `SELECT count(*) FROM (SELECT 1 FROM … WHERE … LIMIT cap + 1)`
  with `cap` defaulting to `10,000`. The response reports `count` (clamped to the cap) plus
  `countCapped`, so clients can render "10,000+". `listRows` accepts a `countCap` override for
  embedders that want a tighter bound.
- **Consequences:** List cost is bounded regardless of table size. Counts above the cap are a lower
  bound, which the response shape makes explicit rather than hiding.

## D-032 — Search tokenises and quotes user input before FTS5

- **Status:** Accepted · 2026-09-22 · implements D-008
- **Context:** FTS5 `MATCH` has its own query syntax. Interpolating user input directly would let a
  stray quote or `OR`/`NOT` change the query, and a syntax error would surface as a `500`.
- **Decision:** `buildMatchExpression` splits the term on whitespace, wraps every token in an FTS5
  string literal (doubling embedded quotes), and appends `*` to the final token for prefix matching.
  Tokens are joined with `AND`. The result is passed as a **bound parameter**, never interpolated
  into SQL. Models without a `searchable` field reject `search` with a `400`.
- **Consequences:** Arbitrary input is safe and behaves like a search box; results are not yet
  ranked by relevance, so search reuses the model's ordering. Relevance ranking would conflict with
  keyset pagination and is deferred.

## D-033 — `mountApi` installs the JSON error and 404 handlers

- **Status:** Accepted · 2026-09-22
- **Context:** Hono carries a sub-app's `onError` handler across `route()`, but **not** its
  `notFound` handler, so an unknown `/api/...` path returned Hono's plain-text `404` even though the
  API app had registered a JSON handler. This was caught by the blog example's tests, not by the API
  package's own tests.
- **Decision:** `mountApi` installs the error and `notFound` handlers on the host app as well as on
  the generated app. Only paths under `/api/` get a JSON body; everything else keeps Hono's
  plain-text `404` so the host application's behaviour is unchanged.
- **Consequences:** API consumers always get JSON, including for unknown endpoints. Host apps that
  define their own `onError` or `notFound` must mount the API first and override afterwards, or use
  `createApiApp` and mount it themselves.

## D-034 — `decimal` uses a Drizzle custom type so major units are used everywhere

- **Status:** Accepted · 2026-09-22 · implements D-006
- **Context:** D-006 stores decimals as integer minor units. M1 stopped at the migration layer, so
  Drizzle returned minor units while the model's TypeScript type promised major units — a mismatch
  waiting to produce off-by-100 bugs.
- **Decision:** `packages/orm/src/schema.ts` declares a `customType` for decimals whose
  `toDriver`/`fromDriver` scale by `10 ** scale`. Minor units now exist only inside the SQL.
- **Consequences:** The model row type is honest: `rating: 12.34` round-trips through Drizzle and
  through the REST API. The migration engine still emits the SQL `DEFAULT` in minor units, so the two
  layers must agree on `scale`; the snapshot records it.

## D-035 — The admin is opt-in and manages its own table through migrations

- **Status:** Accepted · 2026-09-22
- **Context:** M3 ships an unauthenticated admin; the staff gate arrives with the auth adapter in M4.
  Serving `/admin` and `/admin/api` by default would expose every model the moment it is defined.
  The audit log also needs a table, and D-003 says schema is owned by migrations, not by runtime
  `CREATE TABLE IF NOT EXISTS`.
- **Decision:** `defineConfig({ admin: { enabled: true } })` is required. Enabling it registers a
  framework model (`clango.AdminLog`, app label `clango`) through `collectRegistry`, so
  `makemigrations` creates and evolves `clango_admin_log` like any other table. The app label
  `clango` is reserved while the admin is on.
- **Consequences:** Turning the admin on produces a migration, which is exactly what the blog's
  `0002_create_table_clango_admin_log.sql` is. The admin log is excluded from its own metadata and
  from the REST API. `createAdminApp` refuses to start when a logged model lives in a different
  database from the log, because D1 cannot batch across databases and the log must be atomic with
  the mutation.

## D-036 — Cascade previews follow the referential graph transitively

- **Status:** Accepted · 2026-09-22 · implements the M3 delete confirmation
- **Context:** SQLite applies `ON DELETE` actions transitively, so a delete can reach rows two or
  more relations away. A preview that only looked at direct children would under-report and be worse
  than none. Unbounded traversal could also scan an entire database for one confirmation dialog.
- **Decision:** `cascadePreview` walks the graph breadth-first from the deleted row, following only
  `ON DELETE CASCADE` and `ON DELETE SET NULL` edges, collecting affected ids per model up to a
  budget (200 by default). When the budget is exhausted the entry is marked `capped`, which the UI
  renders as "at least N". Ids are queried in chunks of 90 to stay under D1's 100 bound-parameter
  limit (D-009).
- **Consequences:** The confirmation is accurate for ordinary graphs and honest when it is not.
  `RESTRICT` and `NO ACTION` edges are ignored because they block or defer the delete rather than
  touching child rows.

## D-037 — Relation pickers use a dedicated `/options` endpoint

- **Status:** Accepted · 2026-09-22
- **Context:** An admin list shows foreign keys as raw ids, and an edit form needs a searchable
  select. Loading candidate tables client-side is unbounded, and `LIKE '%term%'` is impossible on D1
  (D-008).
- **Decision:** `GET /admin/api/<app>/<model>/options` returns `{ id, label }` pairs, where `label`
  comes from the target's `meta.labelField` (falling back to `id`). It answers three shapes: no
  query returns the first rows ordered by label, `q` searches (FTS5 `MATCH` when the target has
  searchable fields, otherwise an escaped `LIKE 'term%'` prefix capped at 40 bytes), and `ids`
  batches label lookups for the rows on the current page. Results are bounded to 20 by default.
- **Consequences:** List views render names instead of ULIDs with one request per relation column
  per page, and pickers never load a whole table. Models without searchable fields get prefix-only
  matching, which is a deliberate consequence of the `LIKE` cap rather than an oversight.

## D-038 — Admin SPA: HeroUI v3, and the house frontend layout

- **Status:** Accepted · 2026-09-22
- **Context:** The admin SPA is hand-written React, unlike the generated API packages. The project it
  was modelled on (`aiphotoshoot`) has an established frontend layout: `features/<feature>/` with
  `_api`, `_components`, `_types` and `_lib` sub-folders, `src/lib/` for cross-cutting clients,
  `src/components/` for shared UI, `main.tsx` + `router.tsx` at the root, Tailwind CSS v4 with
  `@theme` tokens, TanStack Query for data, and react-router.
- **Decision:** `@clango/admin-ui` follows that layout and uses **HeroUI v3** (`@heroui/styles` +
  `@heroui/react`, Tailwind v4, React Aria) for its controls. Routing uses `createBrowserRouter` with
  `basename`-free `/admin` paths, so `/admin/blog/post`, `/new`, `/:id` and `/:id/delete` are real
  URLs. List state (search, filters, ordering, cursor) lives in the URL, so a list view is
  shareable and the back button works.
- **Consequences:** The hand-rolled path parser from the first draft is gone; react-router owns URL
  parsing. Tests cover the pure modules (`_lib/format.ts`, `_lib/values.ts`, `_lib/model.ts`)
  because the Workers test pool has no DOM, so React rendering is verified by `vite build` and by the
  routing tests in the blog example. The SPA is 232 KB gzipped, dominated by HeroUI's stylesheet;
  that is acceptable for an admin panel behind authentication and off the public critical path, but
  it is the first thing to revisit if the bundle matters.

## D-039 — The generated API keeps role-named modules, not per-feature folders

- **Status:** Accepted · 2026-09-22
- **Context:** The reference backend organises code as `features/<feature>/<feature>.{routes,
controller,service,schema}.ts`. That structure pays off when each feature has hand-written
  endpoints. Clango's API is generated from model definitions, so there is no per-model source file —
  every model is served by the same engine, and copying the folder-per-feature shape would create
  empty ceremony.
- **Decision:** Keep `@clango/api` and `@clango/admin-api` organised by **role** — `routes`,
  `query`/`service`, `validation`, `cursor`, `errors` — which is the same routes/controller/service/
  schema split applied honestly to a generic engine. Adopt the transferable parts of the reference
  layout: query-key modules per concern in the SPA, and thin HTTP handlers over service functions.
- **Consequences:** Adding an endpoint means touching the engine, not creating a folder. If Clango
  later grows hand-written per-feature endpoints, those can live in feature folders beside the
  generated ones without restructuring the engine.

## D-040 — `run_worker_first` must be an explicit positive list

- **Status:** Accepted · 2026-09-22 · corrects the sample in D-018
- **Context:** The first attempt used `run_worker_first: ["/*", "!/admin/*", "!/assets/*"]`. Because
  negative patterns override positives, that also excluded `/admin/api/*`, and the asset layer
  answered `GET /admin/api/meta` with the SPA shell — a `200 text/html` where JSON was expected. It
  was only caught by probing every route against `wrangler dev`.
- **Decision:** List every Worker-owned route positively —
  `run_worker_first: ["/", "/health", "/api/*", "/admin/api/*"]` — and let
  `not_found_handling: "single-page-application"` serve the SPA for everything else. The blog's
  routing test asserts the Worker's side of the boundary: JSON for both API prefixes, and
  non-JSON for `/admin/*`, which is the property that keeps the shell reachable.
- **Consequences:** A forgotten Worker route returns the SPA shell instead of a 404. That failure is
  loud and obvious in a browser, whereas a silently shadowed API path is not — so the positive list
  is the safer default. Documented in `CLAUDE.md` because it is easy to get wrong.

## D-041 — The auth adapter returns identity only

- **Status:** Accepted · 2026-09-22
- **Context:** The spec's `AuthAdapter` returns a user carrying `isStaff` and `isSuperuser`. But
  D-003 says staff flags and permissions are read from Clango's tables, never from the provider's
  record. Having the adapter return those flags would let a provider — or a bug in an adapter —
  claim authority, and it makes the flags ambiguous: which source wins when they disagree?
- **Decision:** `AuthAdapter.getUser` returns `AuthIdentity { id, email }`. `Authorization.resolveUser`
  looks up or creates the `clango_user` row and reads `isStaff`, `isSuperuser` and every grant from
  Clango's tables. New accounts start with no authority, and staff status is only ever granted
  through `clango createsuperuser` or an admin write.
- **Consequences:** A provider cannot escalate privileges, and swapping providers leaves every grant
  intact. The spec's `ClangoUser` shape still exists, but as the _resolved_ user rather than the
  adapter's return type.

## D-042 — Permissions are derived from the registry; grants are stored by codename

- **Status:** Accepted · 2026-09-22 · simplifies the spec's `clango_permission` table
- **Context:** The spec lists `clango_permission` alongside the group and join tables. Seeding it
  would mean a `syncdb`-style write on every deploy, and keeping it in step with the registry as
  models come and go — machinery that exists only to name a fixed, derived list. How permissions are
  _named_ is a framework concern; who holds them is data.
- **Decision:** The catalogue is derived from the model registry: every model contributes
  `<app>.view|add|change|delete_<model>`, including the framework's own tables. Grants reference a
  codename directly (`clango_group_permission.codename`, `clango_user_permission.codename`), so the
  stored tables hold only facts a person decided.
- **Consequences:** No seeding step, no drift, and the catalogue cannot disagree with the code. The
  cost is that a codename is a string rather than a foreign key, so a typo in a hand-written grant
  silently does nothing instead of failing a constraint; the service API and the permission tests are
  the guard against that. Custom (non-model) permissions would need the spec's table and can be added
  later without disturbing this.

## D-043 — Superusers are appointed by email

- **Status:** Accepted · 2026-09-22
- **Context:** `clango createsuperuser` runs in Node with no access to the identity provider's
  tables, and the person being appointed may not have an account yet. Creating the identity would
  mean reimplementing the provider's schema — and its password hashing — in the CLI.
- **Decision:** The command upserts a `clango_user` row by email with staff and superuser flags set.
  `Authorization.resolveUser` matches an authenticated identity by `authId` first and then by email,
  linking the row on first sign-in. The command is idempotent and works against `--local` or
  `--remote` D1 through wrangler, like `migrate`.
- **Consequences:** A superuser can be appointed before they can sign in, and the CLI never touches
  the provider's schema. Emails must therefore be authoritative and stable; a user changing their
  email before first sign-in would need the row updated.

## D-044 — Auth middleware must be registered before the routes it guards

- **Status:** Accepted · 2026-09-22
- **Context:** The first implementation registered `app.use("/admin/api/*", …)` after the model
  routes. Hono runs handlers in registration order, so the middleware never ran and every endpoint
  returned 200 regardless of permission. The permission tests caught it immediately; the earlier
  M3 tests could not, because with auth disabled there is nothing to enforce.
- **Decision:** `createAdminApp` installs the identity middleware and the staff gate before
  registering any route, and the ordering carries a comment saying why. Permission checks inside
  handlers use a single `authorize(c, action)` helper so a new endpoint cannot forget one.
- **Consequences:** Endpoint order in `routes.ts` is load-bearing. Any future middleware for the
  admin API must go in the same block.

## D-045 — The example's dev identity adapter is inert unless explicitly enabled

- **Status:** Accepted · 2026-09-22
- **Context:** The blog needs an authenticated caller to exercise the permission system, but
  Better Auth needs its own migrated schema, which the example does not ship. A header-trusting
  adapter is the obvious shortcut and the obvious footgun: copied into production it would let
  anyone impersonate anyone.
- **Decision:** The blog uses a development adapter that trusts `x-dev-user` **only** when
  `ALLOW_DEV_AUTH === "true"` in the environment. Local development sets it in `.dev.vars`
  (git-ignored, and never deployed); tests set it as a miniflare binding. `createBetterAuthAdapter`
  is the production path, and swapping is one line in `clango.config.ts`.
- **Consequences:** The example demonstrates the real permission flow without shipping a back door.
  The failure mode of a missing `ALLOW_DEV_AUTH` is "nobody is authenticated", which is safe.

## D-046 — The Better Auth adapter is built lazily, per environment

- **Status:** Accepted · 2026-09-22
- **Context:** `clango.config.ts` is evaluated by the Node-based CLI as well as by the Worker, so it
  cannot read a D1 binding: there is no environment at that point. An adapter that accepted a
  database instance could not be configured in the config file at all.
- **Decision:** `createBetterAuthAdapter` takes a **binding name** (default `DB_MAIN`) and a secret
  binding name (default `BETTER_AUTH_SECRET`), and constructs the Better Auth instance on first use,
  memoised per environment in a `WeakMap`. `AuthAdapter.getUser(request, env)` already receives the
  environment, so the binding resolves inside the request.
- **Consequences:** The adapter works identically in the Worker and in tests, secrets stay in the
  environment rather than the config file, and Better Auth is only instantiated for environments
  that actually serve a request. Better Auth's own tables are still the project's responsibility:
  generate them with its CLI and commit the SQL as a migration.

## D-047 — Permissions gate the admin, not the public API

- **Status:** Accepted · 2026-09-22
- **Context:** M4 introduces permissions for every model, and both the admin and the generated REST
  API serve those models. Gating the public API as well would need a policy for anonymous access,
  which the spec does not describe.
- **Decision:** The staff gate and permission checks apply to `/admin` and `/admin/api/*`. The
  generated REST API keeps M2's model: exposure is opt-in per model and per operation
  (`api: { enabled: true, ops: [...] }`), and publishing a model is itself the decision to make it
  public. A project that needs authenticated API access can layer `clangoAuth` and
  `requirePermission` onto those routes itself.
- **Consequences:** The two surfaces have clearly different models: the admin is a privileged
  operator console, the API is an opt-in public interface. If a future milestone wants per-user API
  access, the middleware already exists to compose.
